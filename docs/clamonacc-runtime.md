# clamonacc runtime evidence

Operational on-access scanning depends on more than catalog compilation.
Clamonacc requires a package-provided binary, a reachable clamd instance,
fanotify support in the running kernel, sufficient process capabilities, and
filesystem and security policy that permit marks and quarantine actions.

## Acceptance matrix

The Stage 2 acceptance suite uses privileged, disposable Linux containers so
the test process can exercise fanotify. It installs distribution-native
packages and starts isolated clamd and clamonacc services with a local test
signature database.

| Target | Package integration | Runtime evidence |
|---|---|---|
| Ubuntu 24.04 | Ubuntu distribution packages | Real fanotify detection, path/user exclusions, quarantine, refresh, idempotency |
| Debian 12 | Debian distribution packages | Real fanotify detection, path/user exclusions, quarantine, refresh, idempotency |
| AlmaLinux 9 | EPEL distribution-style packages | Real fanotify detection, path/user exclusions, quarantine, refresh, idempotency |

The smoke target does not establish a support claim and skips this
platform-specific example.

Each supported target proves:

- the distro package supplies an executable clamonacc binary;
- clamonacc connects to an isolated, package-provided clamd binary;
- fanotify watches the configured include path;
- files created in an excluded path remain untouched;
- events generated by the excluded daemon user remain untouched;
- EICAR content created by a non-excluded user is detected and moved through
  clamonacc's native quarantine action;
- detection and quarantine results reach the systemd journal;
- a validated configuration change refreshes the managed service;
- restrictive quarantine permissions remain enforced; and
- a second Puppet application converges without changes.

## Capability boundary

The CI containers are intentionally privileged. A successful container test
does not imply that an arbitrary production container has the capabilities
needed for fanotify. Operators must validate the host kernel, container
runtime, mount namespace, capabilities, and any seccomp policy.

SELinux and AppArmor policy are outside Stage 2. Their later roadmap issues
must validate the same paths and service operations with enforcement enabled.
Likewise, the module does not infer Cisco/Talos installer layouts; the runtime
matrix uses distribution-native integration only.

The acceptance suite uses isolated `/tmp` and `/run` paths, a local EICAR
signature, and disposable services. It never scans production filesystems or
downloads a virus database for the on-access test.
